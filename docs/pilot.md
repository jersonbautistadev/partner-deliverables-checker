# Honest pilot protocol

**Evidence status: not collected.** No real checking times, omissions caught, usage counts or user feedback are claimed. Fictional automated examples demonstrate behavior, not operational benefit.

Start with one coordinator and one contributor, after the web workflow/security gates pass. Get approval to use a small set of actual team publishing instructions and non-sensitive drafts. Keep private files out of public repositories and screenshots.

1. Agree on the authoritative requirement version and a human-reviewed answer key. Mark ambiguous instructions before checking begins. Record how long requirement entry/review takes separately.
2. Choose at least a few representative packages: text-only, text plus image, and one needing subjective review. Use consented real packages or clearly label synthetic defects. Do not mix synthetic defects into real-omission claims.
3. Time the current manual workflow and the app-assisted workflow with a consistent start/end definition: begin with the instructions and files available; end when the reviewer produces their list of findings. Keep upload/setup time in the total or report it separately for both methods.
4. Counterbalance order or use comparable different packages to reduce learning effects. This is a small convenience pilot, so state that it cannot establish broad performance claims.
5. Compare findings against the answer key. Count confirmed omissions, missed problems, false alarms and items needing clarification. Have a coordinator adjudicate disagreements; do not count “needs review” as a confirmed defect.
6. Record usability feedback and errors. Retain anonymized notes with permission. Reproduce and test fixes before repeating the exercise.

Do not extrapolate to all event teams or claim the app prevents all publishing errors.
